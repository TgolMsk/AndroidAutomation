# 万龙助手 · 采集倒计时实时显示 与 ETA 驱动派遣

> 移植自旧版万龙面板的设计文档（2026-09-09 需求与实测）。实例由 `@avdm/core` 的 AVD 提供，
> 设备操作经助手的设备租约与 device-RPC；游戏机制、实测结论与铁律原样保留。

## 需求
1. 每个账号（实例）的每支采集队，**剩余时间实时显示在面板上**。
2. 开启自动采集后，**基于时间触发派遣**：队伍快回来时才去派下一轮，而不是死循环轮询。

## 核心机制：本地递推 + 周期性校准
读一次面板很贵（切界面 + 截图 + 识别，实测单张截图就 ~1.4s），
但倒计时是**确定性递减**的，所以不需要反复读。

```
采样：打开「部队管理」面板 → 识别每行 (状态词, 剩余时间 remaining)
记录：march.etaAt = sampledAt + remaining      // 绝对到期时刻，落盘
显示：UI 每秒本地计算 remaining = etaAt - now  // 零 adb 开销，秒级流畅
校准：满足任一条件时重新采样
       · 距 etaAt < 60s（临界，防漂移误判）
       · 距上次采样 > 周期校准间隔（兜底纠偏）
       · 刚派兵 / 刚召回（状态必然变化）
       · 识别到异常（行数与记录不符、出现未知状态词）
```
> 面板不常驻打开：采样时打开、读完即关，不干扰其它任务。

## 调度：定时器而非轮询
每支队按到期时刻注册一个唤醒：
```
唤醒 → 打开部队管理面板校验（只看不派）→ 队伍确已回归（队列有空位）？
   是 → 检查队列空位 + 指挥官耐力 → 走采集派遣流程（G0–G16，见 流程-采集抓宠清体力.md）
   否 → 用新读到的 remaining 重新注册定时器（说明之前有漂移或队伍被续采）
```
多实例各自独立维护定时器；**同一实例内的 adb 操作必须串行**（实例设备租约），
不同实例之间可并发（受全局并发上限约束）。

**收益**：10 账号 × 5 队轮询式需要几十次截图/分钟；ETA 式在空闲期接近零 adb 调用。

## 数据模型（每实例一份，聚合进面板）
```ts
interface MarchState {
  slot: number            // 面板中的行序（1..N）
  status: string          // 采集中 / 行军中 / 返回中 …（状态词模板识别）
  targetCoord: string     // "607,560"，用于目标去重
  targetType?: string     // 木材/金币/铁矿石/魔水，由缩略图判定
  troopCount?: number
  commanders: { name: string; stamina: [number, number] }[]
  etaAt: number           // 绝对到期时刻（毫秒）——显示与调度都基于它
  sampledAt: number       // 本次读数时刻，用于判断是否该校准
}
interface InstanceQueueState {
  instanceIndex: number   // AVD 实例编号（配合 record.createdAt 做身份校验，绝不持久化 serial）
  accountId: string       // 绑定的账号
  queueUsed: number       // 面板右上 N
  queueTotal: number      // 面板右上 M
  marches: MarchState[]
  lastSampledAt: number
  error?: string
}
```

## 面板 UI
- 采集总览：每实例一张卡片
  - 卡头：实例名 / 账号 / 在线状态 / **队列 4/5**
  - 卡身：每支队一行 —— 资源类型徽章 + 坐标 + **倒计时进度条**（本地每秒递减）
  - 快到期的队伍高亮；异常或识别失败的行标红并显示原因
- 全局汇总条：总队列占用、最近一支队的到期时间、正在执行的任务数

## 待确认（不阻塞开发，出现时补采）
- 状态条绿色填充表示**载重量**而非时间进度（9 小时的队几乎空、9 分钟的队接近满）。
  已用于面板进度条的起点（`fillRatio`），可预判「满载提前返回」。
- 采集完成瞬间的状态词与行为 —— 已确认：自动回城（见下节）。

---
## 【修正】队列释放时刻 = 采集完成 + 回城时间（2026-09-09 确认）
采集完成后队伍**自动回城**，回程耗时约 1 分钟量级，**与资源点距离成正比**。
⇒ 「采集中」倒计时归零时队列并未释放，此时去派兵会失败。

### 完整 ETA 模型
```
dispatchAt      派兵时刻
travelTime      去程耗时 —— **派兵时直接读取**：「创建部队」页行军按钮上显示（实测 00:01:04）
gatherRemaining 部队管理面板「采集中 HH:MM:SS」
gatherDoneAt  = sampledAt + gatherRemaining      // 采集完成时刻（UI 展示的"采集剩余"）
freeAt        = gatherDoneAt + travelTime        // ← 队列真正释放、可派下一轮的时刻
wakeAt        = freeAt + slackSeconds(60) + jitter(0~20s)     ★宁晚勿早
```
- **调度定时器挂在 `freeAt` 上**，不是 `gatherDoneAt`。
- `travelTime` 无需观察或猜测：派兵流程必经「创建部队」页，顺手识别行军按钮上的时间即可，**必须随本次派兵一起记账**（`noteDispatch`）。
  回程距离与去程相同，按同值估算；资源点卡片上的距离（如 18 km）可做交叉校验。
- 唤醒到点只代表「该去看一眼」—— 机器休眠会让定时器滞后，**必须重新读面板校验**。

### UI 展示（面板区分两个阶段）
- 采集阶段：`采集中 HH:MM:SS`（本地递推）
- 回城阶段：`返回中 MM:SS`（gatherDoneAt 之后自动切换显示，无需重新采样）
- 队伍卡片可显示 `可用于下一轮: freeAt` 供用户直观判断

### 对识别的好处
回城阶段无需再开面板采样：到 `gatherDoneAt` 后本地直接切成"返回中"倒计时，
到 `freeAt` 再开面板校验一次即可。**整个采集周期只需 2 次面板采样**（派兵后 1 次 + 临期 1 次）。

## 【放宽】不追求精确到点，宁晚勿早（2026-09-09 明确）
重复采集**不必卡死时间，可以留冗余**。据此的调度策略：

| 项 | 追求精确 | 采用（留冗余） |
|---|---|---|
| 唤醒时刻 | `freeAt - 30s`（提前） | **`freeAt + slack`，slack 默认 60s（延后）** |
| 唤醒后队列未空 | 视为异常，重新采样 | **指数退避重试** 30s→60s→120s，封顶 5min |
| 校准间隔 | 10 分钟 | 15 分钟 |
| 临期校验 | 距 etaAt <60s 必采样 | 不强制，随退避重试自然发生 |

**理由**：提前唤醒一旦有误差就会撞上"队伍还没回来"，白跑一趟识别+重试；
延后唤醒的代价仅是每轮损失几十秒采集时间，但几乎不会失败。
在多账号并发下，稳定性和低开销远比单轮的极致效率重要。

所有冗余量做成可配置（`slackSeconds`、`retryBackoffSeconds`、`calibrateIntervalMin`），想压榨效率时可以自行调小。

> 注意：**UI 倒计时仍然实时**——本地递推不产生任何 adb 开销，放宽的只是"何时去动模拟器"，不是"何时刷新显示"。
> 调度器每次下次唤醒至少间隔 30 秒（地板）。

# 【游戏机制】疲劳期：北京时间 0:00–9:00 采集大幅减速
游戏按**北京时间**把 0:00–9:00 设为疲劳期，该时段采集速度慢很多倍，9 点整恢复正常。

## 这会打破「倒计时线性递减」的前提
上面「剩余时间恰好递减 5:46」是在非疲劳时段做的。跨过 9 点边界后：疲劳期内派出的队伍会显示很长的剩余时间，**9 点一到倒计时骤然缩短**。

后果：
1. 面板的本地递推在疲劳期会**严重高估**剩余时间；
2. `freeAt` 排得太远 ⇒ 队伍早回来了调度还在睡，队列白空着；
3. 而 0–9 点恰恰是挂机过夜的主时段，影响最大。

## 处理方式：在边界主动排一次校准
`planNextWake` 增加两个唤醒候选（仅当有队伍在外时）：
- 北京时间 **09:00 + 30s** —— 「疲劳期结束，重读倒计时」（关键，倒计时会缩短）
- 北京时间 **00:00 + 30s** —— 「进入疲劳期，重读倒计时」（倒计时会变长，危害较小但同样纠偏）

代价是每天多 2 次唤醒，可忽略。不这样做就只能靠 15 分钟的周期校准去碰，最坏白等 15 分钟。

## ★ 时区陷阱（务必注意）
**宿主机时区不一定是北京时间**（旧版开发机是 America/Los_Angeles，本机 18:39 = 北京 09:39）。
所以边界计算**必须显式按 UTC+8**，用 `new Date().getHours()` / `toLocaleString()` 之类的本地时间会差十几个小时。
北京时间只有**一份实现**：`apps/wanlong-assistant/src/shared/time.ts`（`nextCstBoundary` / `cstDateKey` / `formatCst` …），
主进程与渲染进程共用，测试要在 `TZ=America/Los_Angeles` 下跑过跨日/跨边界用例。

## 账号状态刷新频率
- 周期校准：`calibrateIntervalMin`，默认 **15 分钟**
- 另有事件驱动的唤醒：队伍 freeAt+slack、去程队伍抵达、队列有空位、以及上面两个疲劳期边界、健康探针（默认 3 分钟）
- 面板上的倒计时是**本地每秒递推**，不产生 adb 流量；上面这些才是真正去读面板的时刻

## 【量化】深夜疲惫 = 采集速度 −80%，宝石矿不受影响
有了确切倍率，就不必只做「到边界再重读」的事后纠正，可以**当场算准真实完成时刻**。

游戏显示的倒计时是**按采样那一刻的速度**算的，不预判速度变化。换算模型：
把显示剩余时间看成当前速度下的耗时，沿时间轴分段推进，每跨一个边界按速度比换算：
- 跨出疲劳期（速度 ×5）⇒ 剩余耗时 **÷5**
- 跨入疲劳期（速度 ÷5）⇒ 剩余耗时 **×5**
一趟采集可能连跨多个边界（22:00 派出 → 跨午夜 → 再跨 9 点），故用循环。

实现：`fatigueAdjustedDoneAt(sampledAt, remainingMs, {slowdown, exempt})`。
`FATIGUE_SLOWDOWN = 5`（−80%），游戏改版只改这个常量。
`FATIGUE_EXEMPT_RESOURCES = {'gem'}` —— **宝石矿豁免**，豁免时原样返回不做换算。

### 实测验证（闭式换算 vs 逐分钟工作量仿真，两套独立实现互相印证）
| 场景 | 显示剩余 | 直接采信 | 换算后真实完成 | 误差 |
|---|---|---|---|---|
| 北京 01:00 采样 | 10h | 11:00 | **09:24** | 1h36m |
| 北京 22:00 采样 | 4h | 次日 02:00 | **次日 09:12** | **7h12m** |
| 北京 10:00 采样 | 2h | 12:00 | 12:00 | 无（全程正常） |
| 北京 02:00 采样 | 3h | 05:00 | 05:00 | 无（未跨界） |
| 宝石矿 01:00 采样 | 10h | 11:00 | 11:00 | 无（豁免） |

### 为什么值得做
不换算的话，22:00 那个场景下调度会在 02:00 醒来找空位，而队伍要 09:12 才回；
中间 7 小时按退避阶梯每 5 分钟开一次部队管理面板 ⇒ **白开约 84 次**，
且面板整夜显示错误的倒计时。边界重采样只能在 09:00 之后才纠正，来不及。

**边界唤醒仍然保留**，退化为一道校验兜底：预测 + 实测对账，谁错了都能发现。

## 【已修】新接入实例会空转一个校准周期（2026-09-10 多账号实测）
新实例的队列状态未知（从未成功读过面板，queueUsed/queueTotal=null）。`planNextWake` 的「队列有空位，尽快派遣」
候选要求**已知**有空位，未知时不触发，于是只剩 15 分钟的周期校准 —— 实例重启后干等了一个周期。
修法：`hasFreeSlot(state) === null` ⇒ 追加候选「队列状态未知，先读一次面板」（dueAt=now，受 30s 地板约束）。
